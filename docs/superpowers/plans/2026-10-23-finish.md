# Finishing tasks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner pastes a link or says "merge it when done", and `ot` itself records, accepts, merges and cleans up the task. Merge conflicts go back to the task's own worker, and the engine restarts itself after `ot` is updated.

**Architecture:** A new `onethread/finish.py` holds the merge rules (target branch, safety checks, conflict abort) and *standing orders* (meta `finish:<id>`, JSON). The engine runs `finish.tick` every round. `ot finish T [--link URL]` gives an order after one confirmation popup. `ot accept` merges by itself (`merge_on_accept`, default on) by leaving an order behind. `Ops.merge` reuses `finish.merge`. The engine compares a fingerprint of its own code each round and exits so a fresh copy starts.

**Tech Stack:** Python 3.10+ standard library, unittest, SQLite, git.

**Spec:** `docs/superpowers/specs/2026-10-22-finish-and-tips-design.md`, Part 1, the matching "Calls settled" lines, and the Part 3 hooks for `ot finish`. Part 2 (tips) is a later plan.

## Global Constraints

- Standard library only; no new dependencies.
- Never push, open a pull request, post anywhere, or send anything off this machine.
- Never merge into a repo with uncommitted changes or a different branch checked out. Never leave the owner's repo mid-merge (always `git merge --abort` on failure). Never delete an unmerged branch. Never `--force`.
- The owner approves once, in the popup shown when the order is given; the engine's later merge asks nothing more. `merge_on_accept`: the accept popup says "Accept … and merge it into …" and asks nothing more.
- On a conflict the worker **merges the current base into its branch** and resolves there, never rebases.
- Two failed conflict rounds in a row → one offer, order removed.
- A task stacked on another task's branch merges only after that dependency is merged; its target then becomes the repo's own base branch.
- `ot finish --link` on a `done` task stores the link in the task's result (`published`) only, no worker turn.
- The owner never types `ot finish`: the orchestrator runs it when they paste a link or say "merge it".
- Update README, HOW-IT-WORKS, docs/ARCHITECTURE, docs/STATUS and the lobby INSTRUCTIONS in the same change.

## Review Focus

1. The owner's repo has another branch checked out, or uncommitted changes, when the order fires: the repo is untouched, **one** offer (not one per tick), and the merge happens on a later tick once the repo is clean.
2. The task is cancelled while its order waits: the order is dropped and nothing is merged.
3. A conflict twice in a row: one `merge_failed` offer, the order is gone, and the owner's repo has no `MERGE_HEAD` and no changes.
4. `ot finish T --link URL` on a task already merged and cleaned up (done, no worktree): the link is stored, no error, no worker turn.
5. A running worker when the engine restarts for new code: the engine exits between rounds only, never kills the worker (the next engine reattaches it, as today).

### Task 2: Standing orders, run by the engine

**Files:**
- Modify: `onethread/finish.py` (orders, `step`, `tick`)
- Modify: `onethread/model.py` (`"done": {"queued"}`: a conflict sends a done task back to its worker)

- Test: `tests/test_finish.py`, `tests/test_engine.py`

**Interfaces:**
- Consumes: Task 1's `merge`, `target`; `Store.set_meta/get_meta`, `Store.q`, `Store.set_status`, `Store.update_task`, `Store.close_attention`, `Store.add_attention`; `review.mark(store, tid, how)`.
- Produces:
  - `order(store, tid, link="") -> None`: meta `finish:<tid>` = `{"link": link, "link_pending": bool(link), "conflicts": 0}`. If the task is `queued` and a link is given, the followup is appended now and `link_pending` is False.
  - `get_order(store, tid) -> dict | None`, `drop(store, tid) -> None`.
  - `step(store, task) -> str`: one order, one move; returns what happened (`"accepted"`, `"merged"`, `"requeued"`, `"blocked"`, `"conflict"`, `"failed"`, `"waiting"`, `"dropped"`).
  - `tick(store) -> None`: `step` for every `finish:%` meta key; one task's error is logged (`finish_failed`) and the others still run.
  - `LINK_NOTE = "The owner published it: {link}. Record the published link with the work, then stop."`
  - `CONFLICT_NOTE = "{target} moved and your branch no longer merges cleanly. Merge {target} into your branch (do not rebase), resolve the conflicts, run the tests, and commit."`
  - Voice: `"merge_blocked": "{label} is ready to merge, but {note} Fix that and I'll merge it, or later?"`, `"merge_failed": "{label} can't merge: {note} Look at it, or cancel it?"`.

`step` rules:

| task status | order | does |
|---|---|---|
| cancelled | any | drop → `"dropped"` |
| review | `link_pending` | followup `LINK_NOTE`, review → queued, `link_pending` False → `"requeued"` |
| review | otherwise | store `published` in result when a link exists, done, close attention, `review.mark(…, "finish")` → `"accepted"` (merge happens next step) |
| done | any | store `published` if a link exists; `merge`: merged → drop, close `merge_blocked` → `"merged"`; wait → `"waiting"`; blocked → `add_attention(merge_blocked, detail)` → `"blocked"`; conflict → `conflicts+1`; at 2 → `add_attention(merge_failed, detail)`, drop → `"failed"`; else followup `CONFLICT_NOTE`, done → queued → `"conflict"` |
| anything else | any | `"waiting"` (order kept) |

A successful merge resets `conflicts` to 0 only by dropping the order.
